# Terraform (AWS me-central-1)

Everything the apps run on in AWS, in the UAE region. Only **staging** exists so far; production
will be a second folder under `envs/` that calls the same `platform` module with bigger sizes.

**Not applied yet.** The code validates offline (`terraform validate`, also a CI job), but no plan
has been run against an AWS account. That needs credentials and is the first step below.

```
infra/terraform/
  bootstrap/         the S3 bucket for Terraform state. Applied once per account, by a person
  envs/staging/      the staging environment: sizes and names, then `module "platform"`
  modules/
    platform/        one whole environment, wired together (the diagram is at the top of main.tf)
    network/         VPC over 3 zones: public, private (tasks) and database subnets; NAT; S3 endpoint
    ecr/             a container repository per app, immutable tags, scan on push
    ecs-cluster/     Fargate cluster, Cloud Map namespace, task execution role
    ecs-service/     one app: task definition, service, logs, security group, ALB rule, Cloud Map name
    alb/             public load balancer, HTTPS (ACM certificate), HTTP → HTTPS
    rds-postgis/     PostgreSQL 16, Multi-AZ, encrypted, TLS only, backups and point-in-time recovery
    redis/           ElastiCache Redis with TLS and an auth token
    rabbitmq/        Amazon MQ for RabbitMQ, private, AMQPS
    s3-media/        public media bucket behind CloudFront; private, KMS-encrypted KYC bucket
    secrets/         one Secrets Manager secret per environment variable
    ses/             SES domain identity with DKIM, MAIL FROM and DMARC; SMTP credentials
```

## What staging looks like

| Host              | Goes to                      |
| ----------------- | ---------------------------- |
| `<domain>`        | web (the customer app)       |
| `seller.<domain>` | seller                       |
| `admin.<domain>`  | admin                        |
| `api.<domain>`    | gateway (`/api/v1`, `/docs`) |

- One load balancer routes by host name. Every task runs in a private subnet with no public IP.
- The gateway reaches services over TCP at `<service>.staging.am.internal` (Cloud Map). The Next
  apps call the gateway from the server the same way; the browser uses `api.<domain>`.
- **Only the current phase runs.** `current_phase = 0` runs the gateway, identity and the three Next
  apps. Raising it starts the next phase's services (the same list as `SERVICES` in
  `libs/contracts/src/services.ts`). Every app has its ECR repository from the start.
- Postgres, Redis and RabbitMQ accept connections only from the backend tasks' security group, and
  sit in subnets with no route to the internet.
- Staging is sized to be cheap: one NAT gateway, `t4g.micro` database and cache, a single
  RabbitMQ instance, `protect_data = false` so it can be torn down. Postgres is still Multi-AZ, as
  the directive asks.

## Secrets

Each variable is its own secret, `african-market/staging/<NAME>`, injected into the tasks by ECS.

| Secret                                      | Value                                                 |
| ------------------------------------------- | ----------------------------------------------------- |
| `JWT_ACCESS_SECRET`, `OTP_HMAC_SECRET`      | generated by Terraform (64 random characters)         |
| `DATABASE_URL`, `REDIS_URL`, `RABBITMQ_URL` | built from what Terraform created, with its passwords |
| `SMTP_URL`                                  | SES SMTP credentials                                  |
| anything in `manual_secrets`                | a placeholder; set the real value by hand (below)     |

The generated passwords are in the Terraform state, which is why the state bucket is encrypted,
private, versioned and TLS-only. Nothing secret is in this folder or in `terraform.tfvars`.

Set a manual secret:

```bash
aws secretsmanager put-secret-value --region me-central-1 \
  --secret-id african-market/staging/<NAME> --secret-string '<value>'
```

then restart the service (`aws ecs update-service --force-new-deployment ...`) so it reads it.

## Bootstrap (first time, needs AWS credentials)

You need an AWS account with administrator access for the first run, the AWS CLI signed in to it
(`aws sso login` or `aws configure`), Terraform 1.10 or newer, and a domain for staging.

1. **State bucket.** Bucket names are global; if `african-market-terraform-state` is taken, choose
   another and use it in `envs/staging/backend.tfbackend` too.

   ```bash
   cd infra/terraform/bootstrap
   terraform init
   terraform apply            # optionally -var state_bucket=<name>
   ```

   Keep the `terraform.tfstate` this writes somewhere safe (a password manager is fine). It only
   describes the bucket.

2. **Settings.** `cp envs/staging/terraform.tfvars.example envs/staging/terraform.tfvars` and set
   `domain`, plus `route53_zone_id` if the domain's DNS is in Route 53.

3. **Plan.** This is the step F0-13 stops at.

   ```bash
   cd ../envs/staging
   terraform init -backend-config=backend.tfbackend
   terraform plan -out staging.tfplan
   ```

4. **Apply, in two passes.** The services need their images, and the images go into the
   repositories this creates.

   ```bash
   terraform apply -target=module.platform.module.ecr
   # push the images, tagged with a commit: until F0-14 automates it, see infra/docker/README.md
   # (Next images need --build-arg from `terraform output next_public_build_args`)
   terraform apply -var image_tag=<commit>
   ```

   **DNS outside Route 53:** while the second apply waits for the certificate, add the records from
   `terraform output dns_records` (certificate and email), and point the four host names at
   `terraform output load_balancer_dns_name` with CNAME records.

5. **Migrations.** Before the services first start, run each one's migrations as a one-off task:
   its task definition with the command `migrate` (`terraform output migration` has the subnets,
   security groups and task families). F0-14 makes this part of every deploy.

6. **Email.** A new SES account is in the sandbox and only sends to verified addresses. Request
   production access in the SES console (Account dashboard → Request production access) before
   real people sign up by email.

## Known gaps

- **Phone codes on staging.** Identity's real SMS/WhatsApp provider is still a stub that answers
  `SMS_PROVIDER_NOT_CONFIGURED`, and the console provider is refused outside development. Phone
  sign-up on staging needs the WhatsApp provider (P-09); its credentials will be `manual_secrets`.
- **SMTP credentials are an IAM access key**, scoped to sending from the domain. They go away when
  identity gets an SES API provider and sends with its task role.
- **Deploys.** CI building and pushing images, running migrations and rolling out (with GitHub OIDC,
  no stored AWS keys) is F0-14, which will also add the OIDC role.
- **Media domain.** Public media is served from the `*.cloudfront.net` address. A custom name needs a
  certificate in us-east-1 and can come later. CloudFront caches public shop images at edge
  locations outside the UAE; personal and KYC files are never in that bucket.
- **ARM.** Tasks run on x86 because CI builds x86 images. Graviton (ARM64) is cheaper; it needs
  multi-architecture builds.
